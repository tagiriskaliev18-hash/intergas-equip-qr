# Техническое задание (ТЗ)
## Локальное веб-приложение паспортизации, диагностики и контроля ТО оборудования по QR-коду

---

## 1. Общие сведения и назначение системы

### 1.1. Назначение
Веб-приложение (далее — **Система**) является единой мобильной точкой входа в локальную базу технической и эксплуатационной документации оборудования (в формате **PDF**), а также инструментом визуального контроля технического состояния, планирования технического обслуживания (ТО), ведения дефектных ведомостей и расчёта бюджетных потребностей на материалы и ремонт.

Основной сценарий работы: инженер, механик или обслуживающий персонал наводит камеру **смартфона** (подключённого к локальной сети Wi-Fi предприятия) на QR-код, размещённый на единице оборудования, видит распознанную ссылку, переходит в карточку агрегата и получает мгновенный доступ к:
- **паспорту оборудования в формате PDF**;
- **документам диагностики в формате PDF** (при их наличии);
- **графикам ТО** и истории обслуживания;
- **дефектным ведомостям** (скачивание готовых PDF и формирование новых дефектных ведомостей в PDF);
- **фотоосмотрам** (загрузка фотографий со смартфона для визуальной фиксации и оценки технического состояния);
- **спецификации материалов/ЗИП для ТО** и **уведомлениям о приближении сроков ТО** с автоматическим напоминанием заложить необходимую сумму в бюджет.

### 1.2. Ключевые эксплуатационные ограничения
1. **Основное клиентское устройство:** смартфон (Android / iOS, эталон экрана `390×844` и `360×800`), с полной адаптацией интерфейса под планшеты и настольные компьютеры (`1440×900` и выше).
2. **Полная автономность (Offline-first в LAN):** Система обязана работать в закрытом локальном контуре без доступа к сети Интернет. Все шрифты, CSS-стили и JS-библиотеки распознавания QR-кодов размещаются и раздаются локально с сервера Системы (обращения к внешним CDN запрещены).
3. **Локальное хранение на одном компьютере:** все PDF-документы, загруженные фотографии технического состояния и метаданные ТО хранятся локально на том же компьютере, где запущена Система, в выделенной папке `./documents/`. Внешние СУБД не требуются.
4. **Без учётных записей пользователей:** регистрация, аутентификация, ролевая модель и ведение базы пользователей **не реализуются**.
5. **Сетевой режим и HTTPS:**
   - привязка веб-сервера при запуске: **`0.0.0.0`**;
   - TCP-порт: **`5810`**;
   - протокол **HTTPS** с автоматически создаваемым **самоподписанным TLS-сертификатом**, привязанным к адресу **`0.0.0.0`** и локальным IP-адресам сервера (обязательное условие мобильных браузеров для выдачи доступа к системной видеокамере через `MediaDevices.getUserMedia`).

## 2. Технологический стек

| Уровень | Технологическое решение |
| :--- | :--- |
| **Язык и среда выполнения** | Python `3.10+` (рекомендуется `3.12`), **обязательное виртуальное окружение `venv`** |
| **Backend и HTTP/TLS-сервер** | `FastAPI` + `uvicorn` (запуск на `0.0.0.0:5810` с TLS) |
| **Генерация SSL-сертификата** | `cryptography` (автогенерация X.509v3 `cert.pem` и `key.pem` без внешних утилит ОС) |
| **Генерация PDF и QR-этикеток** | `fpdf2` (формирование русскоязычных PDF дефектных ведомостей, графиков и бюджетных сводок с кириллическим TTF-шрифтом), `qrcode` + `Pillow` (генерация QR-стикеров и валидация/ресайз загружаемых фото) |
| **Хранение данных** | Локальная файловая система (`./documents/<equipment_id>/`) + атомарно обновляемый JSON-реестр метаданных (`./documents/registry.json` с файловой блокировкой и записью через `.tmp` → `os.replace`) |
| **Frontend (SPA + Карточка)** | Адаптивный HTML5 + CSS3 + Vanilla ES6 JS; локальный декодер `jsQR` + нативный `BarcodeDetector API`; локальные шрифты `Geist` и `Geist Mono` (`.woff2`) |
| **Тестирование** | `pytest` + `httpx` |

## 3. Функциональные требования

### 3.1. Главный экран (SPA — точка входа, `GET /`)
1. Главный экран работает как одностраничное веб-приложение (SPA) с адаптивным экраном под смартфон.
2. На главном экране размещаются:
   - **Кнопка «Сканировать QR-код»** — основной элемент управления в удобной зоне нажатия большим пальцем.
   - **Блок оперативных уведомлений по ТО и бюджету** — если в базе есть оборудование, у которого приближается срок планового ТО (или ТО просрочено), отображается заметное уведомление с количеством единиц оборудования, ближайшей датой и расчётной суммой, которую необходимо предусмотреть в бюджете.
   - **Быстрый переключатель разделов** (компактный сегментный контрол):
     - *Сканер* — точка входа по QR-коду;
     - *Реестр оборудования* — поиск/переход к карточкам агрегатов и добавление новой единицы оборудования с генерацией QR-этикетки;
     - *План ТО и бюджет* — сводный календарь предстоящих ТО, список необходимых к закупке материалов и итоговая бюджетная потребность.

### 3.2. Работа с системной видеокамерой и распознавание QR-кода
1. При нажатии кнопки **«Сканировать QR-код»** запрашивается доступ к системной видеокамере устройства (`navigator.mediaDevices.getUserMedia({ video: { facingMode: { ideal: "environment" } }, audio: false })`).
2. Видеопоток отображается встроенно на странице (`<video playsinline muted autoplay>`) с прицельной рамкой области наведения и кнопкой **«Остановить сканирование»**.
3. Дополнительно предусматривается резервная кнопка **«Распознать QR с фото»** (`<input type="file" accept="image/*" capture="environment">`) на случай работы с ПК без веб-камеры или ограничения потока браузером.
4. После успешного распознавания QR-кода:
   - видеопоток камеры автоматически останавливается (`MediaStreamTrack.stop()`);
   - на экране отображается **точное распознанное содержимое** QR-кода;
   - отображается активная кнопка **«Перейти по ссылке»** (для корректных URL `https://...`, `http://...`, относительных путей `/doc/<id>` или кодов оборудования `<id>`, преобразуемых в `/doc/<id>`) и кнопка **«Сканировать повторно»**.

### 3.3. Карточка оборудования (`GET /doc/{equipment_id}`)
При переходе по ссылке из QR-кода открывается адаптивная страница конкретного оборудования. Карточка содержит шапку агрегата (наименование, инвентарный номер, цех/участок, текущий статус технического состояния, кнопку скачивания/печати QR-кода) и **4 функциональные вкладки**:

#### 3.3.1. Документация в формате PDF
Все документы хранятся локально в подкаталогах `./documents/{equipment_id}/` и доступны по прямым ссылкам на скачивание в формате **PDF** (а также для быстрого открытия в браузере и загрузки новых файлов):
1. **Паспорт оборудования (`passport/`):**
   - основной технический паспорт изделия в формате PDF;
   - выделенный блок с кнопкой **«Скачать паспорт (PDF)»** и метаданными файла (имя, размер, дата обновления); при отсутствии файла — явный индикатор «Паспорт не загружен» и кнопка загрузки PDF.
2. **Документы диагностики (`diagnostics/`, при наличии):**
   - протоколы вибродиагностики, тепловизионного контроля, дефектоскопии, испытаний изоляции и др. в формате PDF;
   - если диагностика не проводилась и файлов нет, блок корректно отображает статус *«Документы диагностики отсутствуют (по мере проведения загрузите PDF-протокол)»*; при наличии — список файлов со ссылками на скачивание PDF.
3. **Графики и регламенты ТО (`schedule/`):**
   - утверждённые графики ППР / технологические карты ТО в формате PDF со ссылкой на скачивание;
   - кнопка автоматической выгрузки актуального графика ТО данного оборудования в PDF.
4. **Дефектные ведомости (`defects/`):**
   - архив подписанных/сформированных дефектных ведомостей в формате PDF со ссылками на скачивание.

#### 3.3.2. График ТО, материалы для ТО и планирование бюджета
1. **Регламент и график ТО:**
   - для оборудования задаются виды ТО (например: `ТО-1 (ежемесячное)`, `ТО-2 (квартальное)`, `ТР / Капремонт`), периодичность в сутках, дата последнего выполнения и плановая дата следующего ТО;
   - автоматический расчёт остатка дней до ТО и статуса:
     - `В графике` (до ТО более 30 сут.);
     - `Скоро ТО — заложить в бюджет` (до ТО от 8 до 30 сут., настраиваемый порог упреждения);
     - `Срочно ТО` (до ТО 7 сут. и менее);
     - `Просрочено` (плановая дата прошла).
   - возможность зафиксировать выполнение ТО («Отметить ТО выполненным») с пересчётом следующей плановой даты и сохранением записи в истории ТО.
2. **Материалы и ЗИП для ТО:**
   - перечень необходимых расходных материалов, смазочных материалов и запасных частей для проведения ТО: наименование, артикул/марка, требуемое количество, единица измерения (`шт.`, `л`, `кг`, `компл.`), остаток в наличии, ориентировочная цена за единицу (₽);
   - расчёт стоимости сервисных/подрядных работ (при наличии).
3. **Уведомления о бюджете («Предусмотреть суммы в бюджет»):**
   - при наступлении горизонта планирования (по умолчанию за **30 дней** до даты ТО и ближе) Система формирует целевое уведомление в карточке агрегата и в сводном центре уведомлений:
     > *«Внимание: через N дн. плановое ТО ([Вид ТО]). Необходимо предусмотреть в бюджете [Сумма] ₽ (закупка недостающих материалов и ЗИП: [X] ₽, работы: [Y] ₽).»*
   - возможность скачать сводную **Бюджетную заявку на ТО и материалы в формате PDF**.

#### 3.3.3. Фотоосмотр (визуальная оценка технического состояния)
1. Пользователь со смартфона может сделать снимок на камеру или выбрать фотографию из галереи (`JPEG`, `PNG`, `WebP`) и загрузить её в карточку оборудования.
2. При загрузке указываются:
   - визуальная оценка технического состояния: **«Исправно (норма)»**, **«Удовлетворительно (следы износа / замечание)»**, **«Неисправно (требуется ремонт / дефект)»**;
   - осматриваемый узел/агрегат и текстовый комментарий специалиста;
   - автоматическая фиксация даты и времени осмотра.
3. Все фотографии сохраняются локально в `./documents/{equipment_id}/photos/`. Итоговая оценка последнего осмотра автоматически отражается в шапке карточки оборудования, а снимки выстраиваются в наглядную хронологическую ленту состояния (с просмотром в полном размере).

#### 3.3.4. Дефектные ведомости (учёт дефектов и автогенерация PDF)
1. Ведение электронного журнала выявленных дефектов по оборудованию: узел, описание дефекта, степень критичности (`Низкая`, `Средняя`, `Высокая / Аварийная`), рекомендуемое мероприятие (ремонт/замена), оценочная стоимость устранения (₽), статус (`Открыт` / `Устранён`).
2. Кнопка **«Сформировать дефектную ведомость (PDF)»** — сервер автоматически генерирует оформленный русскоязычный PDF-документ дефектной ведомости по открытым дефектам агрегата, сохраняет его локально в `./documents/{equipment_id}/defects/` и сразу предоставляет ссылку на скачивание PDF.

## 4. Требования к сети, порту и самоподписанному сертификату

1. **Параметры запуска сервера:**
   - Хост привязки: **`0.0.0.0`** (обязательно при каждом запуске Приложения).
   - TCP-порт: **`5810`**.
2. **Самоподписанный TLS-сертификат (`certs/cert.pem`, `certs/key.pem`):**
   - генерируется автоматически при первом старте через пакет `cryptography`;
   - срок действия: **365 суток** (совместимость с ограничением Apple iOS Safari `≤ 825` суток);
   - расширение `Subject Alternative Name (SAN)` обязательно включает:
     - **`IPAddress(0.0.0.0)`** — обязательная привязка сертификата на адрес `0.0.0.0`;
     - `IPAddress(127.0.0.1)` и `DNSName("localhost")`;
     - все автоматически обнаруженные локальные IPv4-адреса сетевых адаптеров компьютера (`192.168.x.x`, `10.x.x.x`, `172.16–31.x.x`) и сетевое имя хоста;
   - при смене локального IP-адреса компьютера сертификат автоматически обновляется при запуске, чтобы смартфоны в сети Wi-Fi беспрепятственно устанавливали HTTPS-соединение и получали доступ к видеокамере.

## 5. Дизайн-система, эргономика и UI/UX

1. **Палитра (приборный высококонтрастный интерфейс без визуального шума):**
   - `#09090F` — базовый глубокий фон (`Obsidian Base`);
   - `#12141E` — рабочие панели и секции с тонкой границей `rgba(255,255,255,0.08)`;
   - `#F3F5FA` / `#8B93A7` — основной и вторичный текст высокой читаемости в условиях цеха;
   - `#4B3BFF` (со световым акцентом `#7B2FF7 → #4B3BFF → #1E90FF`) — акцент ключевых действий;
   - `#00F5FF` — эмиссивная индикация прицела QR-сканера и активного TLS-узла;
   - семантические индикаторы ТО и техсостояния: `#10B981` (исправно / в графике), `#F59E0B` (скоро ТО — бюджетное уведомление), `#EF4444` (просрочено / аварийный дефект).
2. **Типографика (self-hosted, офлайн):**
   - `Geist` (`.woff2` локально) — заголовки и интерфейс;
   - `Geist Mono` (`.woff2` локально) — инвентарные коды, даты ТО, суммы бюджета в `₽`, размеры файлов и содержимое QR-кода.
3. **Адаптивность:**
   - эталон мобильного экрана: **iPhone `390×844`** и Android `360×800` (отсутствие горизонтального скролла, высота кнопок `≥ 48–56 px`, компактный сегментный переключатель вкладок, шрифт полей ввода `≥ 16 px`);
   - эталон настольного экрана: **`1440×900`** (двухколоночная приборная сетка для удобной работы главного инженера с графиками ТО, бюджетами и документацией).

## 6. Требования к безопасности и целостности локальных данных

1. **Защита от Path Traversal:** канонизация всех файловых путей через `Path.resolve()` и проверка `is_relative_to(DOCS_DIR.resolve())`. Доступ к файлам вне `./documents/` строго заблокирован.
2. **Валидация загружаемых файлов:**
   - для документов разрешён только формат `.pdf` (с проверкой сигнатуры заголовка `%PDF-` и лимитом размера, по умолчанию до `50 МБ`);
   - для фотоосмотров разрешены только изображения (`JPEG`, `PNG`, `WebP` с проверкой целостности через `Pillow` и лимитом до `20 МБ`).
3. **Атомарность локального реестра:** запись `registry.json` выполняется через потоковую блокировку (`threading.Lock`) и временный файл с атомарной подменой `os.replace`, исключая повреждение файла при одновременной работе нескольких смартфонов.
4. **Безопасность QR-ссылок и имён файлов:** вывод содержимого QR только через `textContent` (защита от XSS), фильтрация опасных URI-схем (`javascript:`, `data:`), передача русских имён PDF при скачивании по стандарту RFC 5987 (`filename*=UTF-8''...`).

### 7.2. Основные HTTP-маршруты
| Метод и маршрут | Назначение |
| :--- | :--- |
| `GET /` | Главный SPA-экран: кнопка «Сканировать QR-код», уведомления ТО/бюджета, реестр |
| `GET /doc/{equipment_id}` | Страница карточки оборудования со ссылками на скачивание PDF, ТО, фото и дефектами |
| `GET /files/{equipment_id}/{category}/{filename}` | Скачивание PDF-документа (`passport`, `diagnostics`, `schedule`, `defects`) или просмотр фото |
| `GET /api/overview` | Сводка оборудования, активные уведомления о скором ТО и расчёт сумм в бюджет |
| `POST /api/equipment` | Добавление новой единицы оборудования в локальную базу |
| `GET /api/equipment/{equipment_id}` | Полные данные карточки оборудования, список локальных PDF и фото |
| `POST /api/equipment/{equipment_id}/documents/{category}` | Загрузка PDF-документа (паспорт, диагностика, график ТО, дефектная ведомость) |
| `POST /api/equipment/{equipment_id}/photos` | Загрузка фотографии со смартфона с оценкой визуального техсостояния |
| `POST /api/equipment/{equipment_id}/maintenance` | Добавление/обновление регламента ТО и норм материалов/ЗИП |
| `POST /api/equipment/{equipment_id}/maintenance/{task_id}/complete` | Отметка о выполнении ТО с пересчётом следующей даты |
| `POST /api/equipment/{equipment_id}/defects` | Добавление записи о дефекте |
| `POST /api/equipment/{equipment_id}/defects/generate-pdf` | Автогенерация печатной Дефектной ведомости в формате PDF в папку `defects/` |
| `GET /api/equipment/{equipment_id}/budget-pdf` | Выгрузка расчёта бюджета и материалов на предстоящее ТО в формате PDF |
| `GET /api/equipment/{equipment_id}/qr` | Генерация PNG-этикетки с QR-кодом ссылки на карточку оборудования |

## 8. Порядок запуска и критерии приёмки

### 8.1. Развёртывание в виртуальном окружении `venv`
```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
python run.py
```

### 8.2. Чек-лист приёмки
1. Приложение развёрнуто в `venv`, автоматически выпускает самоподписанный сертификат с привязкой `0.0.0.0` + локальный IP в `SAN` и слушает `https://0.0.0.0:5810`.
2. Главный экран адаптирован под смартфон (`390×844`) и ПК (`1440×900`), работает офлайн без CDN и не требует регистрации/входа пользователей.
3. Кнопка «Сканировать QR-код» активирует системную камеру, распознаёт QR-код, выводит его содержимое и даёт перейти по ссылке на страницу оборудования.
4. На странице оборудования доступны ссылки на скачивание в формате PDF: паспорта, документов диагностики (с корректной отработкой случая их отсутствия), графиков ТО и дефектных ведомостей из локальной папки `./documents/`.
5. Работает загрузка фотографий со смартфона с выставлением оценки визуального техсостояния и сохранением снимков локально.
6. Работает ведение графиков ТО, материалов/ЗИП и цен, формируются заблаговременные уведомления о наступлении ТО с точным расчётом сумм, которые необходимо предусмотреть в бюджете, а также автогенерация дефектных ведомостей и бюджетных заявок в формате PDF.
